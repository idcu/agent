## 1. 任务边界

### 1.1 核心目标
基于 `docs/评估.md` 中的 5 个核心维度评估框架，对 `docs/tasks` 目录下的所有文档进行标准化和完善。创建标准化文档模板，并按照统一模板对所有任务文档进行整改，确保所有文档具备：明确的任务边界、可量化的验收标准、完整的执行计划、工程化要求和风险应对措施。

### 1.2 不做什么
- 不修改文档的核心业务逻辑内容
- 不删除原有文档中的任何有用信息
- 不创建新的任务文档（仅整改现有文档）
- 不涉及代码实现的修改

### 1.3 输入
- `docs/评估.md` - 评估框架文档
- `docs/tasks/` 目录下所有现有任务文档
- `docs/tasks/reference/task_template.md` - 标准化文档模板

### 1.4 输出
- 所有 `docs/tasks/` 目录下文档按统一模板整改完成
- 完整的整改进度统计
- 更新后的剩余工作清单

### 1.5 前置依赖
- `reference/task_template.md` 已创建完成
- 原任务文档内容已完整保存
- 评估框架文档已阅读并理解

5. 更新剩余工作清单

## 7. 详细实现步骤

### 7.1 整改原则

#### 原则 1：保留原有内容
- 不要删除原文档中的任何有用信息
- 将原有的详细实现步骤移到模板的 "7. 详细实现步骤" 部分
- 将原有的验证检查清单、Git 提交、常见问题排查移到对应章节

#### 原则 2：新增标准化章节
- **1. 任务边界**：明确核心目标、不做什么、输入输出、前置依赖
- **2. 技术实现方案**：核心选型、核心逻辑、数据结构/接口、跨平台适配
- **3. 验收标准**：功能验收、性能验收（可量化）、异常验收
- **4. 执行计划**：工期、里程碑、人力
- **5. 工程化要求**：编码规范、测试要求、部署指引
- **6. 风险与应对**：识别风险并制定应对措施

#### 原则 3：保持格式统一
- 所有文档使用相同的 Markdown 格式
- 文档头部必须包含版本信息、最后更新时间、责任人、任务状态
- 使用统一的章节编号和命名

### 7.2 整改步骤（以单个文档为例）

#### 步骤 1：读取原文档
先完整阅读原文档，了解其内容结构。

#### 步骤 2：复制模板内容
将 `reference/task_template.md` 的内容复制到目标文档。

#### 步骤 3：填充文档头部
```markdown
# 任务 X.X: [原文档标题]

&gt; **文档版本**: v2.0  
&gt; **最后更新**: 2026-04-09  
&gt; **责任人**: IDCU Team  
&gt; **任务状态**: ⏳ 待开始
```

#### 步骤 4：填写 "1. 任务边界"
- **核心目标**：基于原文档的目标，使其更具体、可量化
- **不做什么**：明确排除范围
- **输入**：列出任务的输入数据/参数
- **输出**：列出任务的输出结果/返回值
- **前置依赖**：列出前置任务或条件

#### 步骤 5：填写 "2. 技术实现方案"
- **核心选型**：从原文档中提取技术选型
- **核心逻辑**：用简洁的流程图或步骤列表描述
- **数据结构/接口**：列出关键的数据结构或 API
- **跨平台适配**：说明 Windows/Linux 的差异点

#### 步骤 6：填写 "3. 验收标准"
- **功能验收**：列出具体的、可验证的功能点
- **性能验收**：添加可量化的性能指标（如耗时、内存占用、QPS 等）
- **异常验收**：列出异常场景的处理要求

#### 步骤 7：填写 "4. 执行计划"
- **工期**：从原文档中提取或估算
- **里程碑**：拆分为具体的时间节点
- **人力**：说明需要的人数和技能要求

#### 步骤 8：填写 "5. 工程化要求"
- **编码规范**：对齐项目的 .clang-format 规范
- **测试要求**：说明单元测试覆盖率、测试场景等
- **部署指引**：说明编译命令、部署路径等

#### 步骤 9：填写 "6. 风险与应对"
识别 2-3 个主要风险，并制定应对措施。

#### 步骤 10：迁移原有内容
将原文档中的内容按以下方式迁移：
- 详细的代码实现步骤 → **7. 详细实现步骤**
- 验证检查清单 → **8. 验证检查清单**
- Git 提交命令 → **9. Git 提交**
- 常见问题排查 → **10. 常见问题排查**

### 7.3 关键要点

#### 要点 1：可量化的验收标准
评估文档特别强调验收标准需要可量化。例如：

**不好的例子**：
- 功能正常
- 性能良好

**好的例子**：
- 模块加载时间 ≤ 100ms
- 支持并发 100 个模块加载
- 内存占用 ≤ 512KB/模块
- QPS ≥ 100

#### 要点 2：明确的任务边界
必须明确"做什么"和"不做什么"，避免范围蔓延。

#### 要点 3：跨平台适配
所有涉及代码实现的任务都需要说明 Windows 和 Linux 的差异点。

#### 要点 4：风险识别
每个任务都应该识别至少 2 个主要风险，并给出应对措施。

### 7.4 优先级建议

按照评估文档的建议，按以下优先级进行整改：

#### 最高优先级
1. phase1 剩余文档（项目基础）
2. phase2 文档（核心基础设施）

#### 核心优先级
3. phase3 中的核心库文档（idcu-common、idcu-log、idcu-config 等）

#### 重要优先级
4. phase3 其他文档
5. phase4 文档
6. phase5 文档

## 10. 常见问题排查

| 问题 | 可能原因 | 解决方案 |
|-----|---------|---------|
| 原文档内容丢失 | 迁移过程中误删除 | 使用 Git 恢复原文档，重新迁移 |
| 格式混乱 | 标题层级错误 | 检查并修正 #、##、### 的使用 |
| 验收标准不可量化 | 描述过于模糊 | 将"功能正常"改为具体可验证的指标 |
| 文档头部缺失 | 忘记填充头部信息 | 按照模板补充版本、更新时间等信息 |
