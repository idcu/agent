# 技术决策记录

## 为什么选择 C99 而不是 C11/C17？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定

**原因**:
1. **更广泛的编译器支持** - C99 几乎在所有编译器上都支持
2. **与现有代码库兼容** - 现有项目使用 C99
3. **够用就好** - 我们不需要 C11 的新特性（如 `_Generic`、线程库等）
4. **降低学习成本** - 团队更熟悉 C99

**备选方案**:
- C11: 新特性，但兼容性差
- C++: 功能强大，但复杂度高
- Rust: 内存安全，但学习曲线陡峭

## 为什么自研测试框架而不是用 Unity/Check？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定

**原因**:
1. **更轻量** - 只有几百行代码，无外部依赖
2. **完全控制** - 可以自定义测试输出格式和报告
3. **集成紧密** - 可以直接使用项目的错误码和日志系统
4. **学习成本低** - 自己写的框架，团队更容易理解

**备选方案**:
- Unity: 成熟，但需要额外依赖
- Check: 功能丰富，但复杂度高
- CTest: CMake 自带，但功能有限

## 为什么用 CMake 而不是 Meson/Bazel？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定

**原因**:
1. **业界标准** - CMake 是 C/C++ 项目的事实标准
2. **广泛支持** - 几乎所有 IDE 和工具都支持 CMake
3. **现有经验** - 团队已经熟悉 CMake
4. **与现有项目兼容** - 现有项目使用 CMake

**备选方案**:
- Meson: 更现代，但生态系统小
- Bazel: Google 使用，但学习曲线陡峭
- Autotools: 老旧，不推荐

## 为什么选择微内核架构？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定（第一次开发已验证）

**原因**:
1. **灵活性高** - 可以动态加载/卸载模块
2. **可扩展性好** - 添加新功能不需要修改核心
3. **稳定性好** - 一个模块崩溃不影响整个系统
4. **已验证** - 第一次开发证明这个选择正确

**备选方案**:
- 单体架构: 简单，但扩展性差
- 插件架构: 类似，但微内核更灵活

#### ADR-001: 使用 C99 作为开发语言

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定  
**相关文档**: [技术决策记录](./technical_decisions.md)

**背景**:
项目需要选择一种适合系统级开发的编程语言，考虑到性能、兼容性和团队熟悉度。

**决策**:
选择 C99 作为开发语言。

**原因**:
1. **更广泛的编译器支持** - C99 几乎在所有编译器上都支持
2. **与现有代码库兼容** - 现有项目使用 C99
3. **够用就好** - 我们不需要 C11 的新特性（如 `_Generic`、线程库等）
4. **降低学习成本** - 团队更熟悉 C99

**备选方案**:
- C11: 新特性，但兼容性差
- C++: 功能强大，但复杂度高
- Rust: 内存安全，但学习曲线陡峭

**影响**:
- 正面: 兼容性好，学习成本低
- 负面: 缺少一些现代语言特性

**实施计划**:
- 所有代码使用 C99 标准
- 配置编译器以支持 C99
- 编写代码规范文档

**验证方法**:
- 在多个编译器上测试编译
- 检查代码是否符合 C99 标准

## 为什么选择 YAML 作为配置格式？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定

**原因**:
1. **可读性好** - YAML 比 JSON 更易读易写
2. **支持注释** - 可以在配置文件中添加注释
3. **支持复杂结构** - 支持嵌套结构和数组
4. **广泛使用** - 许多现代工具（如 Kubernetes、Ansible）都使用 YAML

**备选方案**:
- JSON: 简单，但不支持注释
- INI: 简单，但不支持复杂结构
- XML: 功能丰富，但冗长

## 为什么选择 CI/CD 工具？

**决策时间**: 2026-04-08  
**决策者**: 开发团队  
**状态**: 已决定

**原因**:
1. **自动化** - 减少手动操作，提高效率
2. **持续集成** - 及时发现和解决问题
3. **持续部署** - 快速交付新功能
4. **质量保证** - 确保代码质量和测试覆盖率

**备选方案**:
- GitHub Actions: 与 GitHub 集成，使用方便
- Jenkins: 功能丰富，可定制性强
- GitLab CI: 与 GitLab 集成，功能完整

**实施建议**:
- 使用 GitHub Actions 作为主要 CI/CD 工具
- 配置构建、测试、代码质量检查等工作流
- 集成代码覆盖率分析
- 实现自动化部署
