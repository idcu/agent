## 沟通渠道

### 1. Discord/Slack（待建立）

我们计划建立 Discord 或 Slack 社区作为主要的实时沟通渠道。

**频道规划：**
- `#general` - 通用聊天、社区公告
- `#help` - 寻求帮助、解答问题
- `#development` - 开发讨论、技术交流
- `#module-dev` - 模块开发相关讨论
- `#showcase` - 展示你的项目和模块
- `#off-topic` - 闲聊、非技术话题

**加入指南（待建立后更新）：**
1. 访问邀请链接
2. 阅读服务器规则
3. 自我介绍
4. 开始参与！

### 2. GitHub Issues

用于：
- 🐛 报告 Bug
- ✨ 提出功能建议
- 📚 文档问题
- ❓ 一般性问题

**使用建议：**
- 先搜索是否已有类似 Issue
- 选择合适的 Issue 模板
- 提供清晰、详细的信息

### 3. GitHub Discussions

用于：
- 💡 开放性讨论
- 🏗️ 架构设计讨论
- 📋 路线图规划
- 🙋 问答

**与 Issues 的区别：**
- Issues 是跟踪可执行任务（Bug、功能请求）
- Discussions 是更开放的对话和思想交流

### 4. Pull Requests

用于贡献代码。详细请参考 [贡献指南](../CONTRIBUTING.md)。

## 社区规范

### 1. 行为准则

所有社区成员都需要遵守 [贡献者公约](../CODE_OF_CONDUCT.md)。

**核心原则：**
- 尊重和友善
- 包容不同观点
- 建设性批评
- 关注社区整体利益
- 同理心

### 2. 沟通礼仪

**提问时：**
- ✅ 先搜索文档和已有讨论
- ✅ 清晰描述你的问题
- ✅ 提供上下文信息（环境、错误日志等）
- ✅ 保持耐心

**回答时：**
- ✅ 友善和乐于助人
- ✅ 解释清楚，不要假设
- ✅ 欢迎追问
- ✅ 如果你不知道，可以让其他人来回答

**讨论时：**
- ✅ 尊重不同意见
- ✅ 用事实和逻辑支撑观点
- ✅ 接受可能无法达成一致
- ✅ 保持专业和礼貌

### 3. 社区禁忌

❌ **不要：**
- 人身攻击或侮辱
- 发布垃圾信息或广告
- 恶意刷屏
- 泄露他人隐私
- 无意义的 "+1" 或 "me too"（可以使用 emoji 反应）
- 在多个频道重复发送相同内容

✅ **应该：**
- 使用 emoji 反应来表达同意/感谢
- 引用相关消息保持上下文
- 把长对话搬到专门的线程
- 分享有用的资源和链接

## 如何参与

### 1. 新手入门路径

**第一周：了解项目**
- [ ] 阅读 README 和文档
- [ ] 尝试编译和运行项目
- [ ] 完成 [教程系列](./)
- [ ] 加入社区，介绍自己

**第二周：小幅贡献**
- [ ] 修复文档中的拼写错误
- [ ] 改进文档表述
- [ ] 回答简单的问题
- [ ] 报告发现的小 Bug

**第三周及以后：深入参与**
- [ ] 修复 Bug
- [ ] 添加小功能
- [ ] 编写测试
- [ ] 参与代码审查
- [ ] 帮助新成员

### 2. 不同的参与方式

你不需要写代码才能参与社区！

#### 💻 代码贡献
- 修复 Bug
- 实现新功能
- 代码重构
- 性能优化
- 编写测试

#### 📚 文档贡献
- 修正错误
- 补充示例
- 翻译文档
- 编写教程
- 改进说明

#### 💬 社区支持
- 回答问题
- 帮助新成员
- 参与讨论
- 组织活动
-  moderation（未来）

#### 🎨 其他贡献
- 设计 Logo/图标
- 制作演示视频
- 撰写博客文章
- 分享项目

### 3. 获得帮助

**如果你遇到问题：**

1. **自助优先**
   - 阅读文档
   - 搜索 Issues 和 Discussions
   - 查看教程

2. **提问技巧**
   - 说明你想做什么
   - 描述你尝试了什么
   - 提供错误信息
   - 说明你的环境（OS、编译器版本等）

3. **在哪里提问**
   - 简单问题 → Discord/Slack（待建立）
   - 技术问题 → GitHub Discussions
   - Bug 报告 → GitHub Issues

**示例：好的提问 vs 不好的提问**

❌ 不好的：
> "程序不工作，帮忙！"

✅ 好的：
> "我在 Windows 11 上使用 MinGW 编译项目时遇到错误。
> 错误信息是：'undefined reference to idcu_some_function'
> 我已经尝试重新运行 build.bat，但问题仍然存在。
> 有人知道怎么解决吗？"

### 4. 帮助他人

**当你看到问题时：**

- 如果你知道答案，友好地回答
- 如果你不确定，可以说"我觉得可能是..."
- 如果你不知道，可以让其他人来回答
- 把好的资源分享给需要的人

**回答的艺术：**
- 不要只给代码，解释为什么
- 提供多个解决方案（如果有）
- 追问以确保对方理解
- 分享相关文档链接

## 社区角色

### 1. 社区成员

**所有参与者都是社区成员！**

权利：
- 使用项目
- 参与讨论
- 提出建议
- 贡献代码
- 获得帮助

责任：
- 遵守行为准则
- 尊重他人
- 积极参与

### 2. 贡献者

**持续贡献的社区成员。**

成为贡献者：
- 多次有意义的贡献（代码、文档、帮助他人等）
- 被维护者认可

额外权利：
- 可能被邀请加入特定团队
- 在讨论中有更大的话语权

### 3. 维护者

**负责项目日常维护的核心成员。**

职责：
- 审查和合并 PR
- 管理 Issues
- 维护项目质量
- 规划发展方向
- 做出技术决策

### 4. 版主（未来）

**负责社区管理的成员。**

职责：
- 维护社区秩序
- 执行行为准则
- 管理 Discord/Slack 频道
- 组织社区活动

## 常见问题

### Q: 我是新手，可以参与吗？

A: 当然可以！每个贡献者都是从新手开始的。我们有专门的"good first issue"标签，适合新贡献者。

### Q: 我不会写 C 语言，能贡献什么？

A: 很多！你可以：
- 改进文档
- 翻译（如果你懂其他语言）
- 测试和报告 Bug
- 帮助其他用户
- 设计 UI/UX（未来）
- 撰写教程

### Q: 我提出的问题/PR 多久会得到回复？

A: 我们尽力在 24-48 小时内回复。请记住，维护者也是志愿者，有自己的工作和生活。

### Q: 如何让我的 PR 更快被合并？

A:
- 遵循代码规范
- 写清晰的提交信息
- 完整填写 PR 模板
- 确保 CI 检查通过
- 积极回应审查意见

### Q: 我可以成为维护者吗？

A: 是的！维护者是从活跃的贡献者中选拔的。持续做出有价值的贡献，你就有机会被邀请加入维护者团队。

### Q: 社区会建立 Discord/Slack 吗？

A: 是的！我们计划在有足够活跃成员时建立。在此之前，请使用 GitHub Issues 和 Discussions 进行交流。

### Q: 我有其他问题怎么办？

A:
- 创建一个 Issue
- 在 GitHub Discussions 中提问
- 等待社区聊天建立后在那里提问
